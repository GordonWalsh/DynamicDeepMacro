## Core Philosophy: Breadth-Eager, Depth-Lazy

The engine has transitioned away from immediate string slicing and recursive concatenation towards using `Token` objectds as "virtual strings" or "string views". The new architecture embraces the "Depth-Lazy" principle: memory allocation for strings is deferred until the single merged string is actually required. The pipeline treats text as pure geometry for as long as possible, only applying semantic meaning and realizing string memory when strictly required.

## The Four-Phase Execution Pipeline

The monolithic approach of "reading and resolving" simultaneously has been decoupled into four distinct, highly optimized phases.

~~### Phase 1: Lexical Analysis (The Geometric Surveyor)~~
The Lexer is entirely blind to semantic meaning, execution logic, or engine state. Its sole purpose is to resolve structural geometry.

- **$O(N)$ Indexing:** It no longer slices strings or uses regex searches that create memory overhead. It performs a single sweep to bin structural markers as integer indices (Positive for opens, Negative for closes).
- **Zero-Depth Culling:** It uses a strict Rigidity Hierarchy (Top-Down Priority Sweeps) to identify overlapping boundaries. Softer boundaries trapped inside harder boundaries are mathematically "shadowed" and neutralized.
- **String Views:** The Lexer does not output text. It outputs `Token` objects that act as pure String Views, holding a reference to the `root_string` and spatial coordinates (`start`, `end`, and occasionally `separator_idx`).
- **Uniform Output:** It strictly outputs `List[List[Token]]` (Segments), ensuring downstream parsers never need branching logic to handle un-segmented text.

### Phase 2: Parsing & AST Construction (The Semantic Builder)

### Phase 3: AST Reduction / Lowering (The Execution Phase)

This is the semantic evaluation phase. The engine does not build strings here; it _reduces logic_.

- **Evaluation:** Nodes execute their specific logic (e.g., rolling RNG, fetching variables, expanding macros) based on the passed `Context` object.
- **Lowering to Literals:** The ultimate goal of every complex Node is to reduce itself to a flat sequence of purely evaluated elements—specifically, `TextNodes`.
- **List Flattening, Not Concatenation:** Nodes do not concatenate outputs (e.g., `return left + right`). They use Python's highly optimized `list.extend()` to flatten the AST structurally. A parent Node yields a 1D `List[Node]` to its parent.
- **Interleaved Post-Patterns:** If a string must be modified (e.g., via regex), the engine avoids stringifying the entire payload. It interleaves unmodified original text (`TEXT` Tokens) with newly constructed replacement strings (`LITERAL` Tokens).

### Phase 4: Serialization (Stringification)

The final realization of memory.

- The Orchestrator (the root caller) receives the fully reduced, flat 1D list of evaluated `TextNodes`.
- It iterates through the list, triggering the `.payload` property on the underlying Tokens (which finally slices the `root_string` or yields the `LITERAL` text).
- It passes this list of strings to Python's C-backed `"".join()` method, allocating memory for the final output exactly once.

## Architectural Update: Lexer Coordinate Insetting & Token Differentiation

We are abolishing the legacy "strict string reassembly" rule. The Lexer will no longer force `Token` objects to include their structural bounding markers (e.g., `< >`, `{ }`).

Instead, the Lexer will **consume** these wrappers via Coordinate Insetting during the final emission phase, handing the Parser clean, ready-to-execute payloads. Furthermore, the Lexer will perform lightweight $O(k)$ character inspections during this emission phase to assign highly differentiated `TokenType` enums based strictly on data types, completely eliminating raw string manipulation from the Parser.

### The New Lexer/Parser Boundary

- **Lexer (Geometry & Data Type):** Identifies boundaries, consumes wrappers, and assigns base structural types based on character data (e.g., `SCOPE`, `INVOCATION_POSITIONAL`, `ESCAPE`).
- **Parsing Functions (Semantic Meaning):** The Node Parser, Definition Handler, and anything else that receives `Token`s uses the `TokenType` for instantaneous routing, and it handles engine-provided semantic configurations (e.g., Class, Position, Evaluation Timing) in addition to completely user-custom string content.

### Code Implementation Changes Required

- **Lexer Emission Loop:** Modify the final interval-to-Token conversion step. It must now calculate a hardcoded integer inset based on the paired boundary type (e.g., `start+1`, `end-1` for Invocations) and apply it to the emitted `Token`. (Double check best behavior for Definitions.)
- **TokenType Enum Expansion:** Add specific enums for differentiated base types (e.g., `INVOCATION_POSITIONAL`,`INVOCATION_UNSCOPED`, `ESCAPE`, `DEFINITION_MULTILINE`).
    - TODO: Multiline needed? Maybe just truncate the closing `>>` and put the separator after the opening `<<`, then the opening brackets could get dropped from the saved Key-Pattern the same way other syntax characters get dropped.
- **Lexer Inspection Logic:** Add lightweight checks inside the Lexer's final emission loop to route surviving intervals to these new Enums (e.g., `payload.isdigit()` checks for Positional Invocations).
- **Parser Refactor:** Remove structure-/type-checking `.strip()`, `.replace()`, and `.isdigit()` string operations from the AST Node initialization and execution paths. Nodes should now trust that the `token.payload` contains only the meaningful data.
